How to use the solutions

If you are the practice interviewer, read the Interviewer reveals before the session and share each fact only when the candidate asks a question that would uncover it. If you are self-studying, attempt the question first, then compare your path with the model path below.

Each model answer shows one strong path to the root cause. Other orders of investigation are fine if they are structured and prioritised. All facts are invented for practice.

Q1 · Cart additions down 15% in three days

E-commerce marketplace (Flipkart-style) · Metric: Add-to-cart events · Medium

Prompt

Cart additions on a large e-commerce marketplace have fallen about 15% over the last three days. Diagnose the problem.

1. Clarifying questions to ask

  • What exactly counts as a cart addition: a tap on Add to cart, or the item successfully appearing in the cart?
  • Is the 15% across web, iOS and Android, or concentrated on one surface?
  • Sudden step change or gradual decline? Compared with what baseline (same days last week)?
  • Has the data pipeline or event definition changed?

2. Hypothesis buckets

  • Data issue: event renamed, SDK change, delayed pipeline.
  • Internal change: new app release, A/B test, pricing or catalogue change, outage.
  • External: competitor sale, holiday, payment-network issue, news.
  • Segment-specific: one platform, version, region, category or user type.

Interviewer reveals (share only when asked)

  • The drop is almost entirely on the mobile app.
  • Analytics logging has been verified as healthy.
  • No change by city, age or gender.
  • A new app version shipped four days ago that reworked the cart and checkout flow.
  • Android only. Android cart additions on the new version are close to zero; iOS is normal.
  • A few new bug reports mention being unable to check out.

3. Model investigation path

  1. Confirm data quality — logging verified, so the drop is real.
  2. Segment by surface: concentrated on mobile app.
  3. Rule out demographics and location: drop is uniform, which points away from market causes.
  4. Check recent releases: a cart/checkout rework shipped four days ago.
  5. Split by OS and app version: Android new version shows near-zero additions; iOS normal.
  6. Walk the funnel on the affected version: product page views normal, Add-to-cart taps normal, cart-add confirmations missing.

Root cause

A bug in the new Android release breaks the step between tapping Add to cart and the item being saved to the cart (for example a failing API call or a crashed handler). The 15% overall drop is the Android share of traffic hitting zero conversions on that step.

Fix
  • Immediately: roll back or kill-switch the new cart flow on Android; push a hotfix; consider forcing an update.
  • Communicate with support so agents can explain and help affected users.
  • Estimate lost orders and revenue for leadership.
Measure recovery
  • Primary: add-to-cart success rate by OS and app version returns to baseline.
  • Secondary: checkout starts and orders on Android.
  • Guardrail: crash rate, app-store rating, support tickets.
Prevent recurrence
  • Staged rollout (1% → 10% → 50% → 100%) with automatic alerts on funnel-step conversion by version.
  • End-to-end tests for the add-to-cart flow on real Android devices before release.

4. Common mistakes

  • Spending ten minutes on competitors before checking internal releases.
  • Not asking about platform and app version early.
  • Proposing a redesign instead of finding the broken step.

60-second answer

Confirmed the data was real, segmented by surface and found the drop on mobile only, ruled out demographic and market causes because the drop was uniform, then tied it to a release four days ago. Splitting by OS showed Android's new version had near-zero cart additions while taps were normal, so the break is between the tap and the cart save. Roll back, hotfix, and add staged rollouts with per-version funnel alerts.

Q2 · Food-delivery orders down 10% in one city

Food delivery (Swiggy/Zomato-style) · Metric: Completed orders · Medium

Prompt

Completed orders in Bengaluru fell 10% this week versus last week. Other cities are flat. What happened?

1. Clarifying questions to ask

  • Completed orders or placed orders? Week over week, same days?
  • All of Bengaluru or certain zones? All hours or peak hours?
  • Any change to fees, incentives, restaurants or the app this week?

2. Hypothesis buckets

  • Demand: weather, local holiday, competitor promotion.
  • Supply: restaurants offline, rider shortage.
  • Product: payment or address bug for that region.
  • Policy: fee or incentive change.

Interviewer reveals (share only when asked)

  • App sessions in Bengaluru are flat.
  • Menu views and carts are flat, but checkout-to-completion fell.
  • Order cancellations by the platform rose sharply in the evening.
  • Rider log-ins in Bengaluru fell 20% after a rider-incentive change on Monday.

3. Model investigation path

  1. Sessions flat → demand is steady.
  2. Funnel stable until after order placement → issue is fulfilment, not intent.
  3. Platform cancellations up at dinner peak → no rider assigned in time.
  4. Rider supply down 20% after Monday's incentive change.

Root cause

A change to rider incentives in Bengaluru reduced rider log-ins at peak, so orders could not be assigned and were auto-cancelled.

Fix
  • Restore or adjust peak incentives; temporarily raise delivery radius or batching.
  • Show honest ETAs and pause ordering in zones with no riders rather than cancelling after payment.
Measure recovery
  • Rider log-ins at peak, assignment time, platform-cancellation rate, completed orders.
  • Guardrails: rider earnings per hour, cost per order.
Prevent recurrence
  • Test incentive changes in a few zones first; alert on assignment time and cancellations.

4. Common mistakes

  • Assuming a demand problem without checking supply.
  • Ignoring the two-sided nature of the marketplace.

60-second answer

Demand was steady and the funnel was fine until after orders were placed. Platform cancellations jumped at dinner time because riders weren't available: rider log-ins dropped 20% after an incentive change. Restore peak incentives, stop taking orders we can't fulfil, and pilot future incentive changes by zone.

Q3 · Ride cancellations up 25%

Ride-hailing (Uber/Ola-style) · Metric: Cancellation rate · Medium

Prompt

Cancellation rate across the platform rose from 12% to 15% over two weeks. Find the cause.

1. Clarifying questions to ask

  • Rate defined as cancelled ÷ requests? Rider- or driver-initiated?
  • All cities or some? All trip types?
  • Any pricing, matching or app changes in the period?

2. Hypothesis buckets

  • Supply-demand imbalance (events, rain).
  • ETA inaccuracy causing rider cancellations.
  • Driver economics: short trips, long pickups, unattractive destinations.
  • App change exposing new information at a new moment.

Interviewer reveals (share only when asked)

  • Driver-initiated cancellations explain most of the rise.
  • They cluster after the driver sees the drop-off location.
  • A product change two weeks ago added a 'trip details' screen that shows drivers the destination right after they accept.
  • Long airport-bound trips from city edges see the highest cancellations.

3. Model investigation path

  1. Split by canceller → drivers drive the increase.
  2. Split by timing → after acceptance, when trip details appear.
  3. Correlate with release → new trip-details screen shows destination after acceptance.
  4. Segment by trip → long pickups and out-of-zone drop-offs most affected.

Root cause

A new screen shows drivers the destination after they accept; drivers now cancel trips they find unattractive, which they previously completed.

Fix
  • Short term: revert the timing or add a small fee for post-accept cancellations.
  • Longer term: fix economics of unattractive trips (return-trip bonus, long-pickup pay) rather than hiding information.
Measure recovery
  • Driver post-accept cancellation rate, rider wait time, completed trips per hour.
  • Guardrails: driver earnings, rider complaints, fairness across areas.
Prevent recurrence
  • Model behavioural impact of exposing new information; launch with holdouts.

4. Common mistakes

  • Treating cancellation as a single metric instead of splitting by who and when.

60-second answer

The rise was driver cancellations right after accepting, when a new screen revealed the destination. Drivers dropped trips they found unattractive. Revert the timing now, then fix the underlying trip economics and measure post-accept cancellations, wait times and driver earnings.

Q4 · Payment success rate fell from 95% to 91%

Payments gateway (Razorpay/Stripe-style) · Metric: Payment success rate · Hard

Prompt

Payment success rate for merchants dropped from 95% to 91% yesterday afternoon. Diagnose.

1. Clarifying questions to ask

  • Success = successful ÷ attempted? Excluding user-abandoned?
  • All merchants or some? All methods?
  • Sudden or gradual? Still ongoing?

2. Hypothesis buckets

  • Our deploy or config change.
  • Partner outage (bank, card network, UPI switch).
  • Fraud rule change blocking legitimate payments.
  • Merchant integration issue.

Interviewer reveals (share only when asked)

  • Cards and wallets are normal; UPI success fell from 96% to 84%.
  • Failures are concentrated on two large issuer banks.
  • Error codes are mostly timeouts from the bank side.
  • No deploy on our side; one bank posted a maintenance notice late.

3. Model investigation path

  1. Split by method → UPI only.
  2. Split by issuer → two banks.
  3. Error codes → bank-side timeouts.
  4. Check deploys and partner status → bank maintenance window.

Root cause

Unannounced maintenance at two large issuer banks caused UPI timeouts; our system kept routing those transactions without fallback.

Fix
  • Route around unhealthy banks where possible; suggest alternate methods to customers; clear status-page communication to merchants.
  • Ensure idempotent retries so customers aren't double charged.
Measure recovery
  • Success rate by method and issuer, timeout rate, duplicate-charge reports.
Prevent recurrence
  • Real-time issuer health monitoring with automatic routing and alerts; partner escalation contacts.

4. Common mistakes

  • Assuming our code broke before checking partners.
  • Ignoring duplicate charges during recovery.

60-second answer

Breaking the rate down showed only UPI failed, for two banks, with bank-side timeouts and no deploy from us. A bank maintenance window was the cause. Route around unhealthy banks, guide customers to other methods, keep retries idempotent, and build issuer-health monitoring with automatic routing.

Q5 · Credit-card application completions down 20%

Card issuer (American Express-style) · Metric: Applications submitted ÷ started · Medium

Prompt

Digital credit-card application completions dropped 20% this month. Find out why.

1. Clarifying questions to ask

  • Is it completions in count or completion rate?
  • Which channels, devices and steps?
  • Any form, policy or vendor changes?

2. Hypothesis buckets

  • Form or KYC vendor change.
  • Mix shift from new acquisition channel.
  • Eligibility or credit policy change.
  • Technical bug on a device.

Interviewer reveals (share only when asked)

  • Starts are up 30% thanks to a new paid-social campaign.
  • Completion rate is down for new paid-social traffic only; organic users are normal.
  • Paid-social applicants abandon at the income and document step.

3. Model investigation path

  1. Split rate vs volume → rate down, volume up.
  2. Split by channel → only new paid-social traffic converts poorly.
  3. Funnel by step → those users drop at income/documents, suggesting lower eligibility or intent.

Root cause

Mix shift: a new paid-social campaign brought many lower-intent or ineligible applicants who abandon at the income and document step. The product itself is not broken.

Fix
  • Retarget the campaign; add a pre-eligibility check before the long form.
  • Judge channels on approved and activated accounts, not starts.
Measure recovery
  • Completion and approval rate by channel; cost per approved account.
Prevent recurrence
  • Report funnel metrics segmented by acquisition channel by default.

4. Common mistakes

  • Redesigning the form when the traffic changed, not the product.

60-second answer

Starts rose 30% from a new paid-social campaign, but only those users completed less, dropping at income and documents. It's a mix shift, not a product bug. Retarget the campaign, add a pre-eligibility step, and measure channels by approved, activated accounts.

Q6 · Daily active users down 8% on a social app

Social media app · Metric: DAU · Medium

Prompt

DAU fell 8% over the past week. Leadership wants to know why.

1. Clarifying questions to ask

  • How is 'active' defined? Same definition as before?
  • Which platforms, regions, cohorts?

2. Hypothesis buckets

  • Seasonality or holiday.
  • Notification delivery issue.
  • Feed quality or ranking change.
  • Competitor launch.

Interviewer reveals (share only when asked)

  • New user sign-ups are flat; returning user DAU is down.
  • Push notification open rate fell sharply.
  • Android 14 users received far fewer notifications after an OS permission change was handled incorrectly in our latest release.

3. Model investigation path

  1. Decompose DAU → returning users down.
  2. Main entry point for returning users is notifications → open rate dropped.
  3. Split by OS version → Android 14 deliveries down after release.

Root cause

The latest release mishandled the Android notification-permission prompt, so many Android 14 users stopped receiving notifications and opened the app less.

Fix
  • Hotfix the permission flow; re-request permission in context with a clear reason.
Measure recovery
  • Notification delivery and open rate by OS version; returning DAU.
  • Guardrails: opt-out rate, uninstalls.
Prevent recurrence
  • Monitor notification delivery by OS version as a release health metric.

4. Common mistakes

  • Blaming content or competitors without decomposing DAU.

60-second answer

Returning users fell, not new ones. Their main trigger, notifications, collapsed on Android 14 after our release mishandled the permission prompt. Hotfix and re-ask permission in context, and add notification delivery by OS version to release monitoring.

Q7 · Streaming watch time down 12%

Video streaming (Netflix-style) · Metric: Hours watched per member · Medium

Prompt

Average weekly watch time per member fell 12% month over month. Diagnose.

1. Clarifying questions to ask

  • Per member or total? Same comparison period?
  • Any playback, quality or app changes?

2. Hypothesis buckets

  • Content seasonality.
  • Playback quality issues causing early exits.
  • Recommendation change.
  • Competitor content.

Interviewer reveals (share only when asked)

  • Sessions per member are steady; average session length fell.
  • Last month had the finale of a very popular series; this month has no big release.
  • Drop is across all regions and devices.

3. Model investigation path

  1. Uniform across segments → not a device or region bug.
  2. Shorter sessions, not fewer → users still come back.
  3. Compare with content calendar → last month had a major finale.

Root cause

Natural seasonality: last month's spike from a major series finale inflated the baseline; this month returns to normal levels.

Fix
  • No product fix needed; compare against a seasonally adjusted baseline or same period last year.
  • Consider surfacing back-catalogue recommendations after big finales.
Measure recovery
  • Watch time vs seasonal baseline; churn among finale watchers.
Prevent recurrence
  • Annotate dashboards with content releases.

4. Common mistakes

  • Inventing a bug when the baseline was unusually high.

60-second answer

The drop is uniform and session counts are steady, only length fell. Last month had a huge finale that inflated the baseline. This is seasonality; compare against a seasonal baseline and use the moment to promote back-catalogue titles.

The app's rating dropped from 4.5 to 3.9 in two weeks. Why?

60-second answer

Tagging the reviews showed repeated logouts starting with version 6.2, which shortened session timeouts. Restore a sensible timeout with biometric re-login, reply to reviewers, and track re-login frequency per release.

Q9 · Search-to-purchase conversion down 9%

E-commerce search · Metric: Purchases from search ÷ searches · Hard

Prompt

Conversion from search to purchase fell 9% over a week. Diagnose.

1. Clarifying questions to ask

  • Conversion per search or per searcher? Same window?
  • Which languages, categories, platforms?

2. Hypothesis buckets

  • Ranking or index change.
  • Catalogue gaps (out of stock).
  • Price changes.
  • Language or spelling handling.

Interviewer reveals (share only when asked)

  • Search volume is flat. Click-through on results fell; zero-result searches doubled.
  • Zero-result queries are mostly in Hindi and Hinglish.
  • A new tokenizer was deployed to the search service last Tuesday.

3. Model investigation path

  1. Search volume flat, CTR down → results got worse.
  2. Zero-result rate doubled → index or query processing.
  3. Segment by language → Hindi/Hinglish.
  4. Correlate with deploy → new tokenizer.

Root cause

A new tokenizer broke handling of Hindi and transliterated queries, returning zero or poor results.

Fix
  • Roll back the tokenizer for those languages; add multilingual test queries.
Measure recovery
  • Zero-result rate, CTR and conversion by language.
Prevent recurrence
  • Offline search evaluation set covering languages and spelling variants before every ranking deploy.

4. Common mistakes

  • Looking only at overall conversion, not intermediate funnel metrics like CTR and zero-results.

60-second answer

Searches were flat but click-through fell and zero-result searches doubled, mostly for Hindi and Hinglish queries, right after a tokenizer deploy. Roll it back for those languages and require a multilingual evaluation set before search changes.

Q10 · Revenue down while DAU is up

Freemium productivity app · Metric: Monthly revenue · Hard

Prompt

DAU grew 10% this month but subscription revenue fell 5%. Explain.

1. Clarifying questions to ask

  • Revenue recognised or billed? Gross or net of refunds?
  • Which plans and regions?

2. Hypothesis buckets

  • Mix shift to free users.
  • Payment failures (involuntary churn).
  • Price or discount changes.
  • Refunds.

Interviewer reveals (share only when asked)

  • New users are mostly from a student promotion and are on the free tier.
  • Existing paid users: renewal failures rose because card payments failed after a billing provider change.

3. Model investigation path

  1. Decompose → payer conversion down (mix shift), and revenue per payer down.
  2. Renewal failure rate up → billing provider change broke card-on-file renewals.

Root cause

Two causes: a student promotion added many free users (diluting conversion, which is fine), and a billing-provider migration broke card renewals (involuntary churn, which is not).

Fix
  • Fix renewal billing; run dunning (retries, card update emails) for failed renewals.
  • Report free and paid cohorts separately.
Measure recovery
  • Renewal success rate, involuntary churn, revenue per payer.
Prevent recurrence
  • Migration checklists with shadow billing runs before cut-over.

4. Common mistakes

  • Stopping at the first explanation (mix shift) and missing the payment bug.

60-second answer

Revenue = users × payer rate × revenue per payer. DAU rose from free student sign-ups, which is expected dilution. But renewals were also failing after a billing-provider migration. Fix renewals and run dunning, and always look for a second cause.

Q11 · Average order value down 7%

Quick commerce (Blinkit-style) · Metric: AOV · Medium

Prompt

Average order value fell 7% this month. Investigate.

1. Clarifying questions to ask

  • AOV including fees and discounts? Same definition?
  • Which cities and categories?

2. Hypothesis buckets

  • Threshold or fee change.
  • Category mix shift.
  • Discounting.
  • Recommendation module broken.

Interviewer reveals (share only when asked)

  • Price per item is flat; items per order fell.
  • Free-delivery threshold was lowered from ₹199 to ₹99 two weeks ago.
  • Order count rose 12%.

3. Model investigation path

  1. Decompose AOV → items per order down.
  2. Check pricing changes → lower free-delivery threshold.
  3. Order count up → users split baskets into smaller, more frequent orders.

Root cause

Lowering the free-delivery threshold let users place smaller, more frequent orders. AOV fell but order count rose.

Fix
  • Decide on contribution margin, not AOV: if delivery cost per order now exceeds gains, adjust the threshold.
Measure recovery
  • Contribution margin per order and per user, order frequency, delivery cost.
Prevent recurrence
  • Evaluate fee changes on unit economics and total GMV per user, not one metric.

4. Common mistakes

  • Calling lower AOV a problem without checking total revenue and margin.

60-second answer

AOV dropped because items per order fell after the free-delivery threshold was lowered. Orders went up 12%. Whether this is bad depends on contribution margin per user, so judge the change on unit economics, not AOV alone.

  3. KB pipeline → new schedule not re-indexed.
